# 苏作创意台：苏州文化文创三维概念工作台 PRD

> 最新详细设计已升级至 [`2026-10-31-suzuo-creative-workbench-2.0-design.md`](./2026-10-31-suzuo-creative-workbench-2.0-design.md)。本文保留为早期 MVP 基线。

> 文档状态：Draft，供产品评审与后续实现使用
>
> 本文只定义产品目标、行为、范围和验收标准，不代表本轮已经开始实现。

## 1. 产品定义

### 1.1 一句话定位

苏作创意台是一套**语音优先的苏州文化文创设计工作台**：设计师用自然语言表达灵感和判断，系统将其沉淀为文化依据、设计 Brief、2D 概念、Rodin 3D 概念模型、版本记录、评审决策和客户提案。

### 1.2 核心价值

让设计团队在一个项目上下文中完成：

```text
说清楚 → 找依据 → 做概念 → 验证立体形态 → 继续修改 → 比较版本 → 交付提案
```

产品的核心不是“生成一张更好看的图”，而是让每个设计结果都能回答：

- 设计意图是什么？
- 借用了什么文化逻辑？
- 哪些内容是真实来源，哪些是设计转译，哪些是 AI 创作？
- 这一版比上一版改了什么，为什么改？
- 当前结果能否进入客户提案或下一步打样？

### 1.3 首个演示项目

固定为：**苏州园林 × 桌面香插 / 桌面摆件**。

首个项目只验证一条完整闭环，不试图覆盖全部文创品类。

## 2. 背景与问题

### 2.1 目标用户的现实问题

1. 灵感在聊天、图片在生图工具、3D 在另一个平台、修改意见在即时通讯软件，设计上下文不断丢失。
2. 2D 图好看，但无法判断体块、镂空、稳定性和使用方式是否成立。
3. 客户通常说“轻一点”“高级一点”“不要太传统”，这些意见很难直接转成可执行修改。
4. 苏州文化容易被简化为窗格、拱门、山水等表面符号，缺少空间逻辑、材料逻辑和当代生活场景。
5. V1、V2、V3 分散在不同文件夹，无法知道每一版保留了什么、否定了什么。
6. 提案需要重新整理设计说明、文化出处、效果图和版本变化，交付成本高。
7. AI 生成内容容易被误写成文化事实，存在可信度和文化表达风险。

### 2.2 机会判断

通用生成工具解决的是“产生图像”，通用项目管理工具解决的是“安排任务”。本产品要解决的是中间的设计推理链：

```text
文化依据 → 设计转译 → 视觉概念 → 三维验证 → 设计决策 → 交付叙事
```

## 3. 用户与使用场景

### 3.1 主要用户

**文创设计师**：负责提出创意、判断文化转译、选择版本和推动项目。

### 3.2 次要用户

- **设计负责人**：查看项目状态、评审版本、确认方向。
- **品牌方或客户**：查看选定版本、评论和提案，不需要看到内部失败稿。
- **文化顾问/工艺师**：核验文化来源、工艺表达和不宜使用的内容。
- **项目协作者**：补充材料、尺寸、场景或交付信息。

### 3.3 典型场景

设计师在会议或灵感记录时说：

> 我想做一个年轻人会用的苏州园林香插，不要仿古，希望有漏景和留白的感觉。

系统在不要求填写长表单的情况下创建项目、复述理解、整理 Brief、给出文化转译方向并生成第一版概念。

## 4. 产品目标与非目标

### 4.1 产品目标

- 让用户在 10 分钟内从一句口述得到可讨论的 2D 概念和一个 Rodin 3D 概念模型。
- 让用户用一句自然语言完成一次有约束的 V1 → V2 修改。
- 让每个图像、模型和提案内容都能追溯到语音、Brief、文化来源和版本。
- 让设计团队在同一项目页内完成“说、看、改、比、交付”。
- 让文化表达从“表面符号”升级为“可解释的设计转译”。

### 4.2 明确不做

- 精确 CAD、尺寸公差、结构工程和开模文件。
- 生产排程、供应链、成本核算、库存和 ERP。
- 真实布料仿真、精确物理模拟和可制造性承诺。
- 一开始就支持所有品类、所有中国地域文化和所有生成模型。
- 复杂的 ComfyUI 式节点编辑器。
- 让用户先填写主题、品类、风格、材质等大量选项。
- 多人实时编辑同一画布。
- 自动把 AI 推测当作历史事实。

### 4.3 反目标

以下结果即使技术上能运行，也视为产品失败：

- 用户必须先完成复杂表单才能开始表达创意。
- 生成结果漂亮，但无法说明文化来源和设计理由。
- 用户说“只改材质”，系统却改变了形态、功能和文化线索。
- Rodin 失败或图片失败后，项目上下文丢失。
- 客户看到内部草稿、错误模型或未经确认的文化陈述。

## 5. 产品原则

1. **语音是主入口，视觉是事实层**：用户主要通过语音推进，所有理解和变化都必须在界面上可见。
2. **AI 先复述，再执行**：大幅变化必须先展示理解；低风险变化可以直接进入生成队列。
3. **文化先解释，再生成**：先形成文化依据和设计转译，再调用图片或 3D 模型。
4. **版本不可覆盖**：每次生成都产生新版本，旧版本始终可查看和恢复。
5. **设计事实与 AI 假设分开**：任何内容都要标注确认状态和来源。
6. **3D 用于概念验证**：明确概念模型与生产工程文件的边界。
7. **阶段管理轻量化**：管理上下文、决策、阻塞和交付，不复制传统项目管理软件。

## 6. 核心概念与术语

- **语音优先（voice-first）**：语音是主要输入，文字输入是兜底；用户不需要手动填完整表单。
- **设计 Brief**：对目标、场景、功能、风格、文化线索和限制条件的结构化设计理解。
- **文化转译（cultural translation）**：把文化事实或文化逻辑转换成形态、空间、材料、功能和叙事规则。
- **设计补丁（design patch）**：把一句修改意见拆成 `change`、`preserve` 和 `constraint`，用于生成受控的新版本。
- **设计事实层（design truth layer）**：项目中已确认内容、AI 假设、待验证内容和来源的统一视图。
- **可追溯性（provenance）**：资产可以回到产生它的语音、Prompt、Brief 修订、文化来源和生成任务。
- **概念模型（concept model）**：用于验证体块、比例和空间关系的 3D 模型，不等于可生产 CAD。
- **阶段门（stage gate）**：判断项目是否具备进入下一阶段条件的轻量状态，不是复杂审批流。

## 7. 全流程与状态机

### 7.1 主流程

```text
capturing
  → grounding
  → concepting
  → prototyping
  → reviewing
  → presenting
  → archived
```

允许从 `reviewing` 回到 `concepting` 或 `prototyping` 生成新版本，但不得覆盖旧版本。

### 7.2 阶段状态

每个阶段有四种状态：

- `active`：当前正在处理。
- `awaiting_confirmation`：系统已有结果，等待用户确认。
- `blocked`：缺少输入、生成失败或存在需要人工判断的风险。
- `done`：阶段产物已确认并可供后续使用。

### 7.3 阶段定义

| 阶段 | 目标 | 系统产物 | 推进条件 |
| --- | --- | --- | --- |
| 灵感捕捉 Capturing | 把自然表达转成项目意图 | 转写、AI复述、Brief v0 | 用户认可核心理解 |
| 文化依据 Grounding | 找到文化来源并建立转译方向 | 来源卡、文化线索、转译说明 | 事实与创作边界清楚 |
| 概念探索 Concepting | 形成可讨论的视觉方向 | 2D 概念、设计说明 | 方向可进入三维验证 |
| 三维验证 Prototyping | 检查体块与空间关系 | GLB、缩略图、任务记录 | 3D 结果可查看或已记录失败原因 |
| 评审迭代 Reviewing | 形成受控修改和版本决策 | Patch、V2、评审记录 | 选定候选版本 |
| 提案交付 Presenting | 将确认内容整理给客户 | HTML/Markdown/PDF 提案 | 提案内容通过内部确认 |
| 归档复用 Archived | 保留项目记忆和可复用资产 | 项目档案、文化转译条目 | 项目关闭 |

## 8. 功能需求

### 8.1 项目与灵感捕捉

**优先级：P0**

#### 必须支持

- 用户点击麦克风或按住说话开始录音。
- 首轮语音可以直接创建项目，不要求提前选择模板。
- 系统自动生成项目名称，用户可语音或文字修改。
- 保存原始音频（如果用户允许）、实时转写和最终修订文本。
- 将一轮语音标记为：讨论、生成、修改、确认、导出或普通备注。
- 支持文字输入作为语音失败时的兜底。

#### 交互要求

AI 首次响应必须包含：

1. 我理解到的目标。
2. 当前已提取的设计事实。
3. 当前仍然是假设或待确认的内容。
4. 将要执行的下一步。

示例：

> 我理解为：面向年轻用户的现代桌面香插，借用苏州园林的空间层次和漏景关系，不直接复制传统装饰。我先生成一版克制的概念方向，并把材质和香座结构保留为待确认项。

### 8.2 语音意图与设计补丁

**优先级：P0**

系统需要区分四种核心意图：

- `DISCUSS`：只讨论，不生成。
- `GENERATE`：根据当前理解生成图片或 3D。
- `MODIFY`：基于某个版本进行受控修改。
- `CONFIRM`：确认 Brief、版本或阶段推进。
- `EXPORT`：生成提案或资产包。

修改语句必须转换为：

```json
{
  "base_version": "V1",
  "changes": {},
  "preserve": [],
  "constraints": [],
  "source_turn_id": "turn_..."
}
```

例：

```json
{
  "base_version": "V1",
  "changes": {
    "hollow_structure": "simplified",
    "visual_weight": "lighter"
  },
  "preserve": [
    "modern_style",
    "garden_spatial_feeling",
    "incense_holder_function"
  ],
  "constraints": ["base_stable"]
}
```

如果系统无法判断某个字段是否应该变化，应把它放入“待确认”，不能静默修改。

### 8.3 Brief 管理

**优先级：P0**

Brief 字段至少包括：

- 产品类型
- 目标用户
- 使用场景
- 核心功能
- 风格方向
- 文化线索
- 形态假设
- 材质假设
- 尺寸或比例假设
- 必须保留
- 明确避免
- 待确认事项

每个字段都需要保存：

- 当前值
- 来源语音或人工输入
- 状态：`confirmed`、`assumption`、`conflict`、`missing`
- 最后修改时间
- 所属 Brief 修订号

Brief 不能被生成任务静默覆盖。新理解必须产生新的修订。

### 8.4 文化依据与转译

**优先级：P0**

#### 文化内容分类

每条文化内容必须属于以下一种：

- `fact`：有来源的文化事实。
- `translation`：设计团队对文化逻辑的设计转译。
- `generated`：AI 产生的创作假设。
- `to_verify`：需要人工或专家确认的内容。

#### 必须支持

- 记录来源名称、链接或文件位置。
- 显示文化内容进入设计的具体方式。
- 允许用户标记“只作灵感，不作事实陈述”。
- 提案中区分文化事实、设计转译和 AI 创作。
- 禁止系统生成不存在的出处或伪造引用。

#### 首个文化转译样例

```text
园林的漏景
→ 局部开口和前后层次
→ 控制可见范围
→ 让香气、光线或影子参与空间体验
```

系统应优先使用这种“设计逻辑”，而不是直接把传统纹样贴到产品表面。

### 8.5 2D 概念生成

**优先级：P0**

#### 必须支持

- 根据当前 Brief、文化转译和用户确认的约束生成概念图。
- 保存完整输入快照，包括 Brief 修订、文化来源、Prompt 和模型名。
- 显示生成中、成功、失败和重试状态。
- 生成结果必须关联一个 Concept 和一个 DesignVersion。
- 保留历史结果，不让新结果覆盖旧结果。
- 支持用户通过语音要求局部修改。

#### 生成结果需显示

- 设计说明
- 使用的文化线索
- 保留约束
- 当前模型和任务编号
- 是否适合进入三维验证

### 8.6 Rodin 三维概念验证

**优先级：P0**

#### 必须支持

- 从选定 2D 概念和结构化 Brief 发起 Rodin 任务。
- 记录任务状态：`submitted`、`processing`、`completed`、`failed`。
- 记录任务 ID、提交时间、输入文本、关联版本和输出文件。
- 生成完成后展示 GLB 预览，支持旋转、缩放和重新加载。
- 生成失败后允许重试，不丢失原任务和项目上下文。
- 明确标记“概念模型，不是生产 CAD”。

#### 不在 P0 实现

- 网格编辑
- 精确尺寸标注
- 开模分析
- 生产级拓扑优化
- 自动判断模型是否可制造

### 8.7 版本与分支

**优先级：P0**

每次 2D 或 3D 生成都产生新的不可变版本。

版本必须记录：

- 版本号
- 父版本
- 创建时间和创建者
- 触发语音
- Brief 修订号
- 改变字段
- 保留字段
- 关联的 2D、3D 和说明资产
- 生成任务 ID
- 状态：草稿、评审中、已选定、归档、废弃

默认使用线性时间轴。只有用户明确从旧版本另起方向时，才显示分支。

### 8.8 评审与决策

**优先级：P0**

评审页面需要支持：

- V1 与 V2 并排查看。
- 2D 图和 3D 模型同步标识版本。
- 显示“改了什么、保留了什么、为什么改”。
- 语音评论和文字评论。
- 将评论转换成待办或下一轮设计补丁。
- 将一个版本标记为当前候选。
- 记录采用、继续迭代、搁置三种决策。

评审决策必须关联版本和来源语音，不能只保存一个无上下文的“通过”。

### 8.9 提案生成

**优先级：P0**

从当前选定版本自动生成提案，至少包括：

1. 项目名称和一句话概念。
2. 设计目标和使用场景。
3. 文化依据。
4. 文化如何被转译为设计语言。
5. 2D 概念图。
6. 3D 视图或模型链接。
7. 功能、材质和尺寸假设。
8. 版本迭代摘要。
9. 待验证风险。
10. 来源与版权说明。
11. “概念设计，不代表生产技术文件”声明。

提案默认隐藏废弃版本、内部备注、失败任务和未确认的 AI 推测。

首版可以先支持 HTML 或 Markdown 导出，再扩展 PDF。

### 8.10 项目归档与复用

**优先级：P1**

项目归档后仍应可检索：

- 文化线索
- 设计转译方式
- 产品类型
- 材质和功能
- 被采用或被否定的方向
- 相关图片、GLB 和提案

复用时必须创建新项目，不能直接修改历史项目。

## 9. 信息架构与页面

### 9.1 项目首页

显示：

- 项目名称
- 当前阶段
- 当前候选版本
- 最近语音事件
- 待确认事项
- 阻塞项
- 最近生成任务
- 下一步建议

不做泛化 BI 仪表盘，不以任务数量或图表装饰为主。

### 9.2 核心工作台

```text
顶部：项目名称｜阶段轨迹｜当前版本｜生成状态

左侧：对话与语音
      实时转写、AI复述、设计决定、待确认事项

中间：设计画布
      2D概念、Rodin 3D、版本对比、生成进度

右侧：设计事实
      已确认、AI假设、文化依据、约束、风险

底部：常驻语音入口、撤销、比较、确认、导出
```

所有视觉控件主要用于查看、撤销、比较和确认，不用于替代对话输入。

### 9.3 提案视图

提案视图与内部工作台分开，默认只展示确认过的内容，并提供客户可见性控制：

- 客户可见
- 内部备注
- 待验证，不应对外展示

## 10. 核心数据对象

```text
Project
 ├─ BriefRevision[]
 ├─ ConversationTurn[]
 ├─ CulturalReference[]
 ├─ Concept[]
 │   └─ DesignVersion[]
 │       └─ Artifact[]
 ├─ GenerationJob[]
 ├─ ReviewDecision[]
 ├─ StageGate[]
 └─ Deliverable[]
```

### 10.1 关键对象说明

- `Project`：项目容器、阶段、参与者和当前候选版本。
- `BriefRevision`：某一时点的结构化设计理解。
- `ConversationTurn`：语音或文字、转写、AI 复述、意图和确认状态。
- `CulturalReference`：文化来源、分类、来源和设计转译说明。
- `Concept`：一个设计方向。
- `DesignVersion`：不可变的设计版本和父子关系。
- `ChangePatch`：一轮自然语言修改转成的变更、保留和约束。
- `GenerationJob`：图片或 Rodin 任务及其异步状态。
- `Artifact`：图片、GLB、缩略图、说明或提案文件。
- `ReviewDecision`：采用、继续迭代或搁置的决定及理由。
- `Deliverable`：从某个版本导出的客户提案或资产包。

## 11. 错误、恢复与安全边界

### 11.1 生成失败

- 保留原始输入和任务记录。
- 显示失败原因的用户可理解版本。
- 提供重试和修改输入两个路径。
- 不创建看似成功但内容为空的版本。

### 11.2 语音识别错误

- 转写结果必须可编辑。
- AI 执行高风险修改前显示关键字段。
- 用户可以说“刚才不是这个意思”撤销当前理解。

### 11.3 过期任务

如果任务基于旧 Brief 或旧版本提交，完成后标记为 `stale`，不得自动替换当前候选版本。

### 11.4 文化表达风险

- 没有来源的内容不得标记为文化事实。
- 提案必须区分事实、转译和 AI 创作。
- 用户可以把某条文化线索标记为“仅内部灵感”。
- 高风险内容进入待验证状态，而不是自动对外发布。

## 12. 权限与协作范围

### P0

单项目所有者模式，保证单人演示闭环。

### P1

- 设计师：编辑和生成。
- 评审者：评论、确认和选择版本。
- 客户：只读查看和评论。

### P2

文化顾问、工艺师和供应商的定向协作权限。

权限扩展不能改变版本不可覆盖和提案内容分层的规则。

## 13. MVP 范围

### 必须完成

- 单项目工作台。
- 语音或文字输入，语音为主。
- AI 复述和 Brief 状态抽取。
- 文化内容四类标注。
- 一次 2D 概念生成。
- 一次 Rodin Text-to-3D 和 GLB 预览。
- 语音修改转 ChangePatch。
- V1 → V2 版本链和差异说明。
- 阶段状态、待确认项和阻塞项。
- HTML 或 Markdown 提案导出。
- 从资产回溯到语音、Brief、Prompt 和任务 ID。

### P1

- 多人评论。
- PDF 导出。
- 素材与文化转译复用。
- 客户分享链接。
- 文化顾问复核。

### P2

- 系列化产品扩展。
- 材料和工艺约束。
- 打样任务。
- 供应商协作。
- 更细的生产可行性检查。

## 14. 成功指标

### 用户价值指标

- 新用户无需长表单即可开始项目。
- 首次口述到可讨论 2D 概念不超过 10 分钟。
- 首次口述到可旋转 3D 概念不超过 15 分钟，受外部生成服务延迟影响时除外。
- 用户能够用一句话完成受控修改。
- 提案不需要重新手工拼接主要材料。

### 产品质量指标

- 生成资产 90% 以上具备完整来源链。
- 版本差异能够明确列出变化和保留内容。
- Rodin 或图片服务失败后，项目上下文不丢失。
- 未确认文化内容不会默认进入客户版提案。

### 演示验收指标

完成以下脚本即视为 MVP 主流程通过：

```text
“我想做一个年轻人用的苏州园林香插，不要太传统。”
→ 创建项目并生成 Brief
→ 标注园林的空间层次、漏景和留白
→ 生成 2D 概念
→ Rodin 生成 3D
→ “保留漏景，镂空简单一点，底座更稳。”
→ 生成 V2 并展示 V1/V2 差异
→ 锁定候选版本
→ 导出客户提案
```

## 15. 迭代路线

### 阶段一：证明闭环

只做单项目、单文化方向、单个 2D 模型和 Rodin 模型，验证“说、看、改、比、交付”。

### 阶段二：证明复用

增加文化转译条目复用、素材库、多人评审、客户分享和 PDF 导出。

### 阶段三：连接真实生产

增加材料、工艺、打样和供应商任务，但继续明确概念设计与工程生产的边界。

## 16. 关键风险与对策

| 风险 | 对策 |
| --- | --- |
| 文化事实被 AI 编造 | 来源标注、四类分类、专家复核状态 |
| 生成结果漂移 | Brief 修订、锁定字段、ChangePatch、保留约束 |
| Rodin 结果不可生产 | 所有 3D 结果显式标记为概念模型 |
| 语音识别错误 | 可编辑转写、先复述、可撤销 |
| 生成服务不稳定 | 异步任务、重试、失败任务保留、过期任务隔离 |
| 功能变成复杂后台 | 只做阶段、决策和阻塞，不做通用 ERP |
| 文化内容过于表面 | 先建立设计逻辑和转译规则，再生成视觉结果 |

## 17. 产品判断

最重要的产品壁垒不是 Rodin 或某个图片模型，而是以下闭环：

```text
文化来源
  → 文化语义
  → 设计转译规则
  → 2D/3D生成
  → 用户评审
  → 版本与决策数据
  → 更好的下一次转译
```

最终产品承诺可以概括为：

> 设计师只负责表达和判断，系统负责把苏州文化灵感变成有依据、可旋转、可比较、可迭代、可交付的现代文创产品概念。

## 18. MVP 默认决策

以下是为避免实施阶段反复等待确认而做出的产品默认决定；它们属于首版范围，不代表长期限制。

### 18.1 使用与部署

- 首版是单用户、本地运行的桌面浏览器 Demo，不实现注册、登录和组织权限。
- 默认在 Google Chrome 中使用，保留文字输入作为语音能力不可用时的完整兜底。
- 原始录音默认不长期保存；首版保存用户确认后的转写、意图、设计补丁和时间信息。未来需要保存音频时，必须增加明确同意和删除能力。
- 首版中文为唯一产品语言，界面、转写、设计说明和提案均使用简体中文。

### 18.2 语音推进规则

- 用户说“只是讨论”“先别生成”时，系统只能更新对话和假设，不能启动生成任务。
- 用户明确说“生成”“做一版”“转成三维”等指令时，可以直接启动对应任务，同时显示 AI 对本轮输入的复述。
- 涉及删除、覆盖当前候选、对外导出或改变多个已锁定字段时，必须等待用户确认。
- 对不阻塞当前生成的信息使用 `assumption`，不连续追问；假设必须在右侧设计事实面板可见。

### 18.3 文化资料范围

- 首版不自动声称已经建立完整文化知识库。
- Demo 使用少量人工整理、可追溯的“苏州园林空间语言”种子资料，重点覆盖漏景、框景、借景、层次和留白。
- 无来源的模型知识一律进入 `to_verify`，不能进入客户版事实陈述。
- 文化来源先支持人工录入标题、链接和备注；自动联网检索属于后续增强能力。

### 18.4 生成能力

- 2D 概念使用已经打通的独立图片模型，不使用文本推理模型替代图片模型。
- 文本模型负责意图理解、Brief、文化转译、ChangePatch 和提案文案。
- Rodin 首版使用 Text-to-3D：根据选定 2D 概念的设计说明、Brief 和约束组织文本提交，不承诺 3D 与 2D 像素级一致。
- 图片生成与 Rodin 都作为可替换的能力提供方；产品数据对象不能直接依赖某一家供应商的字段结构。
- 外部服务凭证只通过安全凭证注入机制使用，不写入项目文件、日志或导出提案。

### 18.5 版本和生成粒度

- 一个 Concept 代表一个设计方向；同一方向的受控修改形成 V1、V2、V3。
- 用户从历史版本明确提出“另做一个方向”时才创建分支。
- 图片任务成功后创建新设计版本；Rodin 结果作为该版本的关联 3D 资产，不因为轮询状态变化重复增加版本。
- 如果 2D 成功但 Rodin 失败，版本仍然保留，并标记三维验证未完成。
- 如果旧任务晚于新任务完成，结果进入历史并标记 `stale`，不替换当前候选。

### 18.6 提案与交付

- MVP 首先导出单页 HTML 提案，并提供浏览器打印为 PDF 的路径；原生 PDF 生成属于 P1。
- 首版提案仅包含一个选定版本，不提供客户在多个方案间投票。
- GLB 作为单独资产下载或本地预览，不强制嵌入离线 PDF。
- 所有提案必须显示文化内容类别和“概念设计，不是生产技术文件”的声明。

### 18.7 首版验收环境

- 前端：React、Vite、TypeScript，沿用现有项目。
- 后端：FastAPI、Python，沿用现有项目。
- Demo 数据可以使用当前 MemoryStore，但接口和对象命名应为后续持久化保留边界。
- 3D 预览优先使用 Three.js 或其轻量 React 封装，最终选型留给技术计划决定。
- MVP 只保证桌面端 Chrome 的主流程，不承诺移动端和其他浏览器体验。

## 19. 需求追踪与发布门槛

后续实施计划应为每项 P0 需求分配唯一编号，并至少覆盖以下发布门槛：

| 门槛 | 必须证明 |
| --- | --- |
| G1 意图成立 | 语音/文字能生成可编辑 Brief，且原始内容可追溯 |
| G2 文化成立 | 至少一条文化事实和一条设计转译被正确区分 |
| G3 概念成立 | 真实图片接口生成 2D 概念并记录输入快照 |
| G4 三维成立 | 真实 Rodin 任务完成并在工作台展示 GLB |
| G5 修改成立 | 一句语音修改生成 ChangePatch 和不可变 V2 |
| G6 决策成立 | V1/V2 差异可见，候选版本可被明确锁定 |
| G7 交付成立 | HTML 提案只包含确认内容并带来源和风险声明 |
| G8 恢复成立 | 图片或 Rodin 失败后能重试且上下文不丢失 |

只有 G1 至 G8 全部通过，才能称为“全流程 MVP 已完成”。
